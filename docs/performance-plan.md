# 优化计划（performance plan）

> **Last reviewed:** 2026-11-24 · **Last updated:** 2026-11-24 · **Change:** 第一版。测量阶段收口
> （四条尺子 + 三方对照），这份是"接下来切哪几刀、按什么顺序、怎么算赢"。
> 现状数字见 [performance.md](performance.md) 与四张生成的页：[commands](performance-commands.md)、
> [functions](performance-functions.md)、[shapes](performance-shapes.md)、[ui](performance-ui.md)。

## 0. 一句话

**每一刀都由发现它的那把尺子验收，并且必须和 Excel/WPS 同口径比。** 只看自己的数字不算数——
上一把刀（`edit.clearAll` 9.13 s → 1.40 s）就是形状尺子发现的，同一把尺子验收的。

## 1. 判定（每把刀都按这个验收）

| 项 | 规矩 |
|---|---|
| **尺子** | 形状刀用 `bench-shapes`，函数刀用 `bench-functions`，场景刀用 `cargo xtask perf`，帧刀用 `bench-ui`。不另造尺子。 |
| **对手** | 同口径的 Excel / WPS 数字（`gate_ext.ps1`、`shapes_ext.ps1` 的 COM 重放）；没有对手的（帧时间）只跟预算比，并在页面写明。 |
| **噪声** | 6–8 组交错 A/B + 符号检验；这台机器的 run-to-run σ 约 10 %，单次差异不算赢。 |
| **门禁** | 59 条预算不许红；一刀改变了某条预算的合理值，同 commit 改 `xtask/perf-budgets.txt` 并写明理由。 |
| **交付** | 一刀一个 commit（`M6: …`），代码 + 生成的页 + `gaps` 条目同 commit。 |
| **不破** | wasm 能编、`cargo xtask ci` 全绿、`never-crash` 规矩不破（不加 `unwrap`、不放开递归）。 |

## 3. 第一批就切这三刀

1. **查找**（2–3 h）：最小、最干净、有 1893× 的对照；早停就赢。
2. **排序**（3–6 h）：最大的单笔用户等待，且和 #2 共享"块搬"。
3. **移动块**（4–6 h）：和排序同一原语，一起做能省一半设计时间。

三刀都靠"**按块搬，不要按格搬**"这一个想法；切完用形状尺子一次性验收（12 条命令 × 3 个摆法），
再看 #4 复制、#5 清格式能不能顺手吃掉。

## 5. 风险与依赖

- **形状尺子只有 12 条命令**：P0 切完，要把尺子扩到更多命令（表格命令、结构编辑、粘贴），否则下一个 O(列) 的坑看不见。
- **Excel 对照是 COM 重放**：查找、筛选两行的语义不完全等价（页面已注明）；新增对照时要写清"两边各做了什么"。
- **安静机**：A/B 必须等负载 < 25 %、无游戏进程；忙机器上的数字是负载，不是代码。
- **每批收尾**：跑一次门禁（59 条）、重出四张页、重出报告（`plan/bench/report.ps1` 或 `extract.py` + specboard）。

## 11. round 52：那 1.2 s 不是"每格读取价"，是二次扫描（11-24）

- **上一轮的判断错了，先纠正**：第 9/10 节把 cut 的 1.2 s 写成"存储层的每格读取价，只有按行打包搬
  能到 ~1.2 s"。实测对照：同样是 800 万格，**高表（8 列/行）cut 只用 0.30 s，宽表（1000 列/行）
  1.20 s**——同一份代码、同样的格子，宽表贵四倍，这不是格子的价钱，是**每行格数**的价钱。
- **真正的原因**：`PackCursor` 是所有行遍历的游标（`iter_range`/`row`/`row_reader`/`iter_scan`/
  `visit_values`/cut 的 `take_rows`），它每一格都调 `BandRow::kind_at` / `style_at`，而这两个函数
  **每次都从行的第一条 run 从头找**。宽表一行是"数字、数量、价格、名称、地区、日期、键、值"循环，
  一千列就是约 250 条 kind run：1000 格 × 平均 125 条 run = 一行 12.5 万步，8000 行 = 10⁹ 步。
- **修法**：游标里带两个 `RunPos`（"上次答的是第几条 run + 它的第一格"，两个词，不借用，所以
  `ScanWalk` 那种自己持有 `Arc<Band>` 的遍历也能存住），一格 O(1) 摊销；`Band::cell_at`/`value_at`
  拆出 `cell_of`/`value_of`，把遍历已经知道的 kind/style 传进去，单格读者保留自己的那一次查找。
- **数字（形状页，每行五次采样）**：
  - cut 本身 **1.20 s → 0.25 s**
  - `range.move` 2.03 → **1.11 s** ✅（目标 2 s；Excel 0.507）
  - `data.sortAscending` 1.81 → **0.83 s** ✅（Excel 0.146）
  - `file.saveBytes` 宽表 1.32 → **0.86 s**
  - `edit.copy` 宽表 852 → **557 ms**
  - 高表的移动 1.30 → 1.39（三次全量跑在 1.28–1.39 之间抖；这次改动碰不到 8 列宽的行）

## 12. round 53：整列参数（P1 第一刀）（11-24）

  `VLOOKUP` 80、`XLOOKUP` 82、`MATCH` 56、`SUMIFS` 40、`SUMIF` 31、`COUNTIF` 27、`SUMPRODUCT` 26。

- **第一件：精确查找先把整列搬进数组再找。** `MATCH(k, A:A, 0)`、`VLOOKUP(k, A:B, n, FALSE)`
  走的是函数库：求值器先把整块物化成 `Value` 数组（`A:B` 在 100 万行是 200 万个），才开始找键。
  键在第一行也要付整张表的钱。**修法**：round 39 给 `XLOOKUP` 加的"按列扫、命中即停"的钩子
  （`first_match_in_column`）推广到数字键，`MATCH`/`VLOOKUP` 接上：行 1 命中 **0.6–0.9 ms**
  （原 25–40 ms），命中在中间就是扫描价，未命中是一次扫描而不是"数组 + 扫描"。

- **第二件：求和先问"这列有主吗"再求和。** `visit_aggregate` 开头跑 `has_owned_cells`（逐行走一遍，

  **修法**：先在一份累加器副本上折，碰到第一个"有主"的格子再交给原来的路径；纯值列一次走完。
- **第三件：一列一行一格，行遍历却收一行的固定开销。** 通用 packed 遍历里**一列读 16.9 ns/格，

## 13. round 54：动态数组分组（P1 第二刀）（11-24）

- **组键曾经是一个 `String`。** `UNIQUE`/`GROUPBY`/`PIVOTBY` 把每一行的键"拼成字符串"
  （`row_key`：长度 + 冒号 + 值的文本形式，文本还转小写），再用这个字符串当 HashMap 的键。
  100 万行就是 **100 万次字符串分配 + 100 万次小字符串哈希**；`PIVOTBY` 的单元格表还用
  两个字符串当键。另外 `UNIQUE`/`GROUPBY` 先把键收进 `Vec<Vec<Value>>`，又是百万次分配。
- **修法**：`KeyIds` —— 按首次出现顺序给每个不同的键一个密集 id；一行的 id 由它值的哈希得到
  （两个 `Vec` + 一张"哈希→第一个 id"的表 + 冲突链），**一行一次哈希、零分配**。撞哈希就把两行
  逐值比较一遍，所以冲突只是多一次比较，不会分错组。哈希和比较共用同一条规则（也就是字符串键
  那条）：数字按值（`-0` 就是 `0`、两个 NaN 位相同才相等）、文本**不区分大小写**、错误按错误码、
  空白彼此相等、数组看第一个值。
- `PIVOTBY` 还额外改了两处：每个桶不再先把值攒成 `Vec<&Value>`（内置聚合直接边走边算，
  `aggregate_rows`，省下 400 万个指针），行/列合计的行号收集一次，不再遍历所有单元格。
- **数字（函数页，每行五次采样，同一天）**：
  - `PIVOTBY` 5.16 s → **989 ms（−81%）** ✅
  - `GROUPBY` 2.48 s → **785 ms（−68%）** ✅
  - `UNIQUE` 1.49 s → **310 ms（−79%）** ✅
  - `BYROW` 1.18 → 1.15 s（**没动**，见下）
  - 同一页上这轮碰不到的行：`BYCOL` 330→312、`SORT` 269→256、`SORTBY` 297→291、`MAP` 554→532、
    `SCAN` 617→601、`DROP` 791→744、`VSTACK` 201→192、`BITAND` 243→232 —— 全部小幅变快 2–13%，
    说明这天窗口本身快一点，所以上面的 −68%〜−81% 是这一轮的净效果。
- **`BYROW` 没动，原因是求值器**：它每行调一次 LAMBDA，而每次调用要先给这一行建一个 `Vec`、
    再包成 `Arc<Array>`、再建一个绑定参数的 `Vec` 并克隆参数名 —— 一行一微秒（100 万行 1.15 s）。
    这是求值器的活（绑定参数改借用、行数组改视图），下一刀再说。
- **测试**：把**旧的字符串键**留在测试里当参照，和新 id 在多组"规则不显然"的值上比：
  `"a"`/`"A"`、`-0`/`0`、两个 NaN、开尔文符号 `K` 对 `"k"`、`"ß"` 对 `"SS"`、空白、错误、
  混合类型行——两边分组必须一模一样。哈希与比较一旦不一致，这个测试就红。

## 14. round 55：LAMBDA 调用本身（P1 第二项收尾）（11-25）

- **上一轮留下的 `BYROW` 1.15 s**，先用探针拆开（`fn_probe` 新增三行）：
  - `LAMBDA(x,1)`（空体）**0.48~0.59 µs/次** —— 说明贵在"调用本身"，不在函数体；
  - `LAMBDA(x,SUM(x))` 再加约 0.3 µs/次 —— 体内一个工作表函数还要额外付钱。
- **三个原因，每次调用各一份**：
  1. `call_lambda_values` 每次把整个环境换掉（`mem::replace(&mut self.env, l.env.clone())`），
     而内联写的 `LAMBDA(x, …)` 捕获环境是空的 —— 于是它马上要用的那个 Vec **被丢弃（连容量）再重建**，
     一百万次；
  2. 每个 helper 用 `vec![(参数.clone(), 值)]` 绑参数 —— 每次一个 Vec + 一次字符串克隆；
  3. `aggregate_value` 每个参数都查**两个**函数名（`SUM` 和 `COUNT`），而 `SUM`/`AVERAGE` 只需要
     `SUM`、`COUNT` 只需要 `COUNT`。
- **修法**：捕获环境为空时**保留现有环境**（`extend` + `truncate`，容量复用；捕获环境非空时仍替换，
  那是词法作用域要的）；新增 `call_lambda_one` 直接把参数推进环境；`aggregate_value` 只查需要的那个名字；
  `MAP` 单数组单参数走同一条路。
- **数字（函数页，每行五次采样，同一天）**：
  - `BYROW` 1.15 s → **984 ms（−14%）** ✅
  - `MAP` 532 → **422 ms（−21%）**、`SCAN` 601 → **524 ms（−13%）**、`REDUCE` 170 → **133 ms（−22%）**
  - 在 `fn_probe` 里更细：`BYROW` 三列 1.16 s → 990 ms，单列 988 → 825 ms，空体 592 → 525 ms，
    `MAP(x,SUM(x))` 885 → 705 ms，`MAP(x,x*2)` 541 → 432 ms
  - **对照**：不跑 LAMBDA 的行没动（`PIVOTBY` 989→990、`GROUPBY` 785→782、`UNIQUE` 310→305、
    `SORT` 256→257、`VSTACK` 192→190），说明机器状态稳定。
- **P1 第二项到此收尾**：四个动态数组函数全部进 1 秒（`PIVOTBY` 990 ms 是压线的，`BYROW` 984 ms）。
- **还剩的**：环境里参数名每次仍分配一个 `String`（要让环境存 `Arc<str>`，全链改一点，收益几个百分点）；
  `BYROW` 剩下的主要成本是这一行自己的 `Vec` + `Arc<Array>`，而参数必须是"拥有的数组"（LAMBDA 可能留着它）。

## 15. round 56：把查找的"写法"补齐（P1 第一项收尾）（11-25）

- **发现**：round 53 教会了 `MATCH`/`VLOOKUP`"扫列命中即停"，但**函数目录里、也是大多数人写的**是带选项的
  写法：`XLOOKUP($K,$KG,$R,1,0,1)`（六个参数）、`XMATCH($K,$KG,0,1)`（四个参数）。这两个直接掉回老路
  （先把整块搬进数组），于是 `XLOOKUP` 74 ms、`XMATCH` 53 ms，而三个参数的 `MATCH`/`VLOOKUP` 只要 17 ms。
- **原因**：窄路要求"正好三个参数"，`XMATCH` 干脆没有窄路（派发表从 `MATCH` 直接掉到 `builtin`）。
- **修法**：`XLOOKUP` 接受 3~6 个参数 —— `if_not_found` 只在没命中时才求值（和老路一样惰性），
  文档默认值（精确匹配、从前往后）可以显式写出来；`XMATCH` 拿到 `MATCH` 那条扫描（match_mode 0、
  search_mode 1 或默认）。其它模式（从后往前、二分、通配符、小于等于）和带通配符的键**一律退回库函数**，
  所以答案不可能变。
- **数字（函数页，每行五次采样，同一天）**：
  - `XLOOKUP` 74 → **16 ms（−78%）** ✅
  - `XMATCH` 53 → **16 ms（−70%）** ✅
  - `MATCH`/`VLOOKUP` 16–17 ms（不变）
  - **对照**：这轮碰不到的行没动（`SUM` 30→29、`COUNTIF` 23→23、`SUMIF` 27→27、`MEDIAN` 51→49、
    `SUMPRODUCT` 23→22、`BYROW` 984→983、`PIVOTBY` 990→996、`BITAND` 231→231）
- **P1 第一项还剩最后一点**：`COUNTIF`（23 ms）/`SUMIF`（27 ms）**为了测一个条件先把整列搬成数组**；
  `MEDIAN`/`SUMPRODUCT`（49/22 ms）本来就要每个值。注意：**改成扫描的底价是 ~19 ms**（一列 100 万行的读取价，
  见 round 52 的 `gaps` §39），所以要真到 10 ms，得在存储层把"读一列"再做紧一次 —— 那是单独一刀，
  而不是函数层的活。
## 16. round 57：criteria 函数改成扫存储（P1 第一项收尾）（11-25）

- **上一轮留下的账**：`COUNTIF` 23 ms、`SUMIF` 27 ms，原因是它们吃 `Array`，所以求值器先把整列搬成
  数组再问条件（100 万个 `Value`）。
- **为什么不是"接一下就行"**：条件本身是个已解析的匹配器（`crates/functions/src/criteria.rs`：
  运算符 + 操作数 + 通配符 token），但它的 `matches` 收 `&Value` —— 存储层遍历时每格都得先造一个
  `Value`，那正是数组搬运已经在付的钱。
- **修法**：匹配器改写成对着一个 `CellView` 判（数字、借来的文本、布尔、错误、空白），于是宿主可以
  直接拿打包好的格子问它、零分配。`COUNTIF`/`SUMIF` 变成**一趟扫存储**（`countif_column` /
  `sumif_columns`；空白 = 遍历没遇到的槽位，条件是"匹配空白"时补上计数）。`SUMIF` 的一列写法
  （`SUMIF(A:A,">0",A:A)` 和两参数的 `SUMIF(A:A,">0")`）也只扫一遍。
- **数字（函数页，每行五次采样）**：`COUNTIF` 23 → **18 ms（−22%）**、`SUMIF` 27 → **18 ms（−33%）**；
  对照未动（`AVERAGEIF` 27→27、`COUNTIFS` 24→24、`SUMIFS` 31→31、`SUM` 29→29、`MEDIAN` 49→50、
  `SUMPRODUCT` 22→22、`MATCH` 16→17、`BYROW` 983→966、`PIVOTBY` 996→990）。
  18 ms 就是"扫一遍"的底价（一列 100 万格 ~19 ns/格）—— 所以 10 ms 的目标不在函数层，在存储层。
- **差分测试抓到新路的两个 bug**：`crates/engine/tests/criteria_scan.rs` 把同一个问题分别写成
  `COUNTIF`/`COUNTIFS`（一对条件）和 `SUMIF`/`SUMIFS`，在一张有数字、数字文本、两种大小写的文本、
  字面通配符、布尔、错误、中间空洞、空字符串的表上比。它抓到：(1) **命中的错误格必须是答案**
  （`SUMIF` 其求和列命中 `#DIV/0!` 时返回错误而不是跳过），(2) 双列写法必须把目标格的错误
  留到这一行的条件判定之后再算。两个都修了并钉住。
- **还剩**：`AVERAGEIF`（27 ms，仍走库）；`MEDIAN`/`SUMPRODUCT`（50/22 ms）本来就要每个值。
## 17. round 58：数组抬升的假设被推翻（11-25，量完不动手）

- **计划里的第 10 项**写的是"抬升是逐元素装箱，≈120 ns/元素，按块处理能到 80 ms"。我先用量把一次调用
  拆成两半——同样的 100 万元素结果，一次折成标量（不铺 spill）、一次留成数组：
  - `SUM(A2:A1000001)` = **16 ms**（读一列 + 折叠）
  - `SUM(BITAND(A2:A,B2:B))` = **87 ms**（多出来的 ~71 ms 就是抬升）
  - `BITAND(A2:A,B2:B)` = **230 ms**（再多的 ~143 ms 是**把 100 万格 spill 铺出去**）
- **所以 230 ms 里抬升只占 71，铺 spill 占 143。** 计划的前提错了：把抬升按块提速，也到不了 80 ms。
- **143 ms 又花在哪**（逐项停掉量出来的）：**~48 ms** 往 `Sheet::spill`（`BTreeMap<CellRef, Value>`，
  一格一个节点）插 100 万条；**~95 ms** 是铺开的其余部分——足迹检查（逐格问"这里有没有东西"）、
  逐格取值克隆、以及这块区域的依赖查询。
- **两个改法，量完都撤回**（按仓库的规矩）：
  1. 足迹检查从"逐格两次查表"改成"位图扫描 + spill 表的区间查询"：**231 → 223 ms**，在噪声里。
     顺带发现区间查询的真 bug：以格子为键的 `BTreeMap` 对"一列的矩形"只能回答超集（它还会命中
     其它列的同几行）——修好之后一起撤回。
  2. 用有序块一次性 `BTreeMap::extend` 铺 spill：**229 → 234 ms**，没有收益，撤回。
- **结论**：第 10 项要动的是**spill 的存储表示**（按区间存 `Arc<Array>`），不是抬升的循环。
  这一刀会牵动所有读 `sheet.spill` 的地方（保存、显示、calc 宿主、清 spill 的命令），需要单独一轮设计。
- **留下的仪器**：`fn_probe` 的三行（`SUM of a lift`、`BITAND, spilling`、`SUM of a column`）。
## 18. round 59：单条件家族全部走扫描（11-25）

- round 57 把 `COUNTIF`/`SUMIF` 改成扫存储，但带一对条件的复数写法（`COUNTIFS`/`SUMIFS`/`AVERAGEIFS`）
  和 `AVERAGEIF` 还是走库（先物化整列）。
- **改法**：宿主的钩子合成一个 —— `criteria_columns(target, criteria, criterion, fold)`，`fold` 是

  求值器按每个函数自己的参数顺序传：`SUMIF(range, crit, [sum_range])` 对 `SUMIFS(sum_range, range, crit)`。
- **保留的差异**：Excel 文档写明的差异——超过 255 个 UTF-16 单位的文本条件，单条件函数是 `#VALUE!`，
  复数形式**截断**。两条路各自解析自己的条件，测试把两种行为都钉住（`COUNTIFS` 260 字符 = 0，
  `COUNTIF` 同样文本 = `#VALUE!`，`AVERAGEIFS` 没命中 = `#DIV/0!`）。
- **数字（函数页，每行五次采样）**：`AVERAGEIF` 27 → **17 ms**、`AVERAGEIFS` 28 → **18**、
  `COUNTIFS` 24 → **18**、`SUMIFS` 31 → **18**；`COUNTIF`/`SUMIF` 保持 18。
  **单条件家族的七种写法现在都在 17–18 ms**（就是"扫一列 100 万格"的价）。
  对照未动（`SUM` 29→29、`MEDIAN` 50→52、`SUMPRODUCT` 22→23、`MATCH` 17→17、`BYROW` 966→978、
  `PIVOTBY` 990→1.00 s、`BITAND` 229→227、`VSTACK` 192→200）。
- **P1 第一项剩下的**：本来就要每个值的 `MEDIAN`/`SUMPRODUCT`（52/23 ms）；要整体进 10 ms，得再拧紧
  存储层"读一列"（`gaps` §39/§40）。
## 19. round 60：一列读取的"找行"占了 62%（11-25）

- **先做消融**（把一列读取的每一段分别去掉，各建一次、各量一次）：
  | 版本 | ns/格 |
  |---|---:|
  | 只走行（不看 kind、不取 payload、不查公式） | **9.8** |
  | + kind 的 run | 11.2 |
  | + payload 与数字表 | 14.8 |
  | + 公式检查 | 15.9 |
  也就是说**一列读的 62% 花在"把行数出来"上**：每行都按 key 去查（`row_bits` 测位 + popcount + 索引到
  `rows`），而"行映射是恒等"的普通表里，一个 band 的 rows **本来就是**它持有的那些 key，而且是排好的。
- **改法**：恒等行映射时直接**顺序走 band 的 rows**（不再每行查一遍），映射过的表（插过/删过行）保留老路，
  那条路要负责逻辑行→物理行。
- **数字**：
  - `visit_packed` 一列：**15.9 → 11.9 ns/格（−25%）**；`visit_values` 一列 ~17.5 → 14.4
  - 函数页（每行五次采样）：`SUM`/`COUNT`/`MAX`/`MIN`/`AVERAGE` **29–32 → 25–26 ms**；
    `COUNTIF`/`SUMIF`/`AVERAGEIF` **17–18 → 15–16**；`MATCH`/`VLOOKUP`/`XLOOKUP` **17 → 15–16**；
    `MEDIAN` 52 → 48、`LARGE` 26 → 23、`SUMPRODUCT` 23 → 21；`FILTER` 81 → 78、`VSTACK` 200 → 190
- **这一刀同时证明了一件事**：100 万行的一列读取**什么都不做也要 9.8 ms**。所以计划里"整个家族 ≤10 ms"
  的目标，撞的就是"把行数出来"这堵墙。要再往下走只有两条：给 band 加一个"所有行都是满的、且从第 0 列开始"
  的标记（那样一列的 payload 就是固定步长，一次装载一行），或者换 spill 的存储（round 58 的结论）。
